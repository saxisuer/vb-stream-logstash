# 峰值行速率口径修正——秒级分桶（Second-Bucket Peak）设计

日期：2026-08-31 · 状态：已批准（用户确认"只改峰值行"方案后直接执行）

## 1. 背景与问题

峰值行（同日 peak-metrics spec）的速率峰值粒度 = **统计窗口（≈10s）均值的会话最高**。WSL2 基线实测暴露系统性失真：20 万条消息 ~1 秒内到达（真实 ~54MB/s），统计行却显示 19.5k msg/s / 4.4MB/s——**固定 10s 分母把突发速率摊薄约 10 倍**，峰值行继承同一失真。用户依据峰值行判读"管线只有 5MB/s"的误导即源于此。

吞吐行**不改**：窗口均值是"这 10 秒整体如何"的观察面，摊薄对它是定义而非缺陷；峰值行才是"最高跑过多快"的语义，必须反映真实突发。

## 2. 设计：秒级分桶峰值

六项速率计数各配一个**秒桶**（`secNo / curCount / peakPerSec` 三 long）：

- **写入**（埋点热路径，各自单写者线程——slot/组装 reader、输出 consumer）：`bump(nanos, delta)`——秒号（`nanoTime / 1_000_000_000`）变化即结算上一秒（`peak = max(peak, cur)`）并重置；同秒累计。一次时钟读数服务同埋点的多个计数（slot 字节/条数共用、输出 records/tx 共用）。
- **报告**（consumer 线程，弱一致读，与现有 LongAdder 语义一致）：`max(peakPerSec, curCount)`——**未结算的当前桶计数作为下界候选**（悬空桶问题：最后一条消息后秒不走满、无人触发结算，取 max 保证最后一秒的突发不丢；未满桶的计数是该秒速率的下界，不会高估）。
- **语义**：峰值行速率段从"最高窗口均值"改为**"会话内最高单秒速率"**；格式不变。分布段（耗时/大小 max）不受摊薄影响，不动。
- **边界效应**：消息横跨秒号会拆两桶（首尾桶不满），秒峰为下界、逐步收敛——秒级粒度本就是近似，可接受。
- **时钟注入**：测试构造器注入受控 `LongSupplier`（默认 `System::nanoTime`），与现有 `baselineNanos` 注入同思路——秒桶行为可确定性驱动。

## 3. 热路径成本

每条消息一次 `System.nanoTime()`（~25ns）+ 一次秒号比较；结算摊销每秒一次。相对现有每条消息的 byte[] 分配与 CQ append（µs 级）可忽略。

## 4. 测试

- 突发不摊薄（核心）：受控时钟同秒灌 2000 条 → 推进 1 秒结算 → reportLines 峰值段 ≥ 2000 msg/s（旧口径按窗口只会显示摊薄值）
- 悬空桶下界：当前秒未结算时直接报告，峰值 ≥ 当前桶计数
- 首窗 n/a、跨秒结算重置、现有峰值行用例期望值适配（同秒灌入的量即秒峰值）

## 5. 不做的事（YAGNI）

- 吞吐行不改（窗口均值语义保留）
- 亚秒滑动窗、活跃时长分母（复杂度高收益边际）
- 秒桶直方图化（只取 max）
