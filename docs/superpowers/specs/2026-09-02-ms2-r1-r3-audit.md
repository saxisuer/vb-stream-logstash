线程安全)与 R3('R' 的 JDBC 元数据查询连接独占),以及 §10 MS2 验收行的"R1/R3 审计"。

## R1:dispatcher 单写者清单

设计红线:dispatch 从 consumer 线程发起,心跳/信号等旁路事件调用线程需改道或验证无
共享可变态。MS2 实际线程拓扑(vanilla 差异:vanilla 的 streaming 源单线程内联处理全部
消息,本连接器拆为监督壳 + reader + consumer 三线程):

| # | dispatcher/共享状态调用面 | 线程 | 依据(源码位) |
|---|---|---|---|
| 1 | `dispatchTransactionStartedEvent`(事务头 BEGIN 记录) | **仅 consumer**(`transaction-consumer`) | `DispatcherTransactionListener.onBegin`,经 `TransactionConsumer.processBucket` 的事件回调 |
| 2 | `dispatchDataChangeEvent`(逐行数据记录) | **仅 consumer** | `DispatcherTransactionListener.onRowChange` |
| 3 | `dispatchTransactionCommittedEvent`(事务尾 END 记录) | **仅 consumer** | `DispatcherTransactionListener.onEnd` |
| 4 | schema 写(`StreamPostgresSchema.applySchemaChangesForTable`/`tableFor`) | **仅 consumer** | 同 listener 的 onRowChange(版本安装,值相等短路);快照阶段 MS2 恒 skipped,无第二写者(MS5 引入真快照时须重审) |
| 5 | offset 写(`PostgresOffsetContext.updateCommitPosition`/`updateWalPosition`) | **仅 consumer** | 同 listener 的 onBegin/onRowChange——`PostgresOffsetContext`/`SourceInfo` 非线程安全,单写者假设的落点 |
| 6 | `BucketTableResolver.bind`(桶快照绑定)/`resolve`(asOf 解析) | **仅 consumer**(同线程先后) | `TransactionConsumer.processBucket` 在 Begin 前 `bind(bucket.relationSnapshot)`;listener 在 TxChange 内 `resolve`——Task 5 的同线程契约成立(接缝无并发原语的前提) |
| 7 | `dispatchHeartbeatEventAlsoToIncrementalSnapshot`(心跳) | **仅监督壳**(coordinator 线程,`supervise` 200ms 空转周期) | `PostgresStreamStreamingChangeEventSource.supervise`;heartbeat.interval 缺省 0 时 Heartbeat 内部 no-op |

旁路面核对:

- **心跳**(行 7):与 consumer 共享的可变态有二——①`ChangeEventQueue`(其本身为并发安全
  设计,阻塞 enqueue,vanilla 同款跨线程用法);②**读 `effectiveOffset`(已知无害项,见下)**。
  心跳不经过 TransactionMonitor(`NotThreadSafe`),不触 schema/offset 写。
- **信号**:`SignalProcessor` 以自身线程周期轮询,但 MS2 无已启用的信号通道
  (`signal.enabled` 缺省 false,process 空转);不写 dispatcher。MS3+ 接信号时重审
  (其表读取与 consumer 的 dispatch 并发面归 R2/MS5 同族)。
- **通知**:`NotificationService` 经 `dispatcher::enqueueNotification` 出口,默认无通道
  不发射。
- **TransactionMonitor 状态机**(每事务计数/事务 id):唯一写路径 = consumer 的数据/事务
  事件(行 1-3);心跳不进 Monitor。**事务 id 同源性已由 Task 8 IT 钉死**——
  `dispatchTransactionStartedEvent(Long.toString(xid))` 必须与
  `StreamEventMetadataProvider.getTransactionId` 的返回同源,否则 Monitor 在首个数据事件处
  按"事务变更"补发一对空 END+BEGIN(IT 实测修复,见 task-8-report)。

**已知无害项(心跳跨线程读 offset)**:监督壳的心跳把 `effectiveOffset`(volatile 字段,
写点在 consumer 的行 5)交给 `dispatchHeartbeatEventAlsoToIncrementalSnapshot`——心跳记录
构建时会读该 offset 的 map,属**跨线程读单写者可变对象**:可能观察到相邻更新间的混合快照
(如 tx N 的 lsn 配 tx N+1 的 table 字段),仅影响心跳记录自身携带的 offset 面,不影响数据
记录;且 `heartbeat.interval.ms` 缺省 0(心跳关闭)时整条路径 no-op。处置:**MS2 接受为
已知无害**(默认关闭 + 影响面限于心跳记录);MS5 做指标/心跳专项时二选一收敛——读侧快照
隔离,或把心跳发射挪到 consumer 空转周期(监督壳只置标志)。

## R3:main JDBC 连接 reader 线程独占

设计红线:'R' 消息的 JDBC 元数据 enrich 在 reader 线程,与快照/信号共享连接需串行化。
MS2 的 main 连接(`PostgresConnection`,由 `DefaultMainConnectionProvidingConnectionFactory`
提供)全生命周期接触面与**时序独占**证明:

| 阶段 | 线程 | 接触面 | 与 reader 的并发 |
|---|---|---|---|
| 任务装配 `PostgresStreamConnectorTask.start` | Connect 任务启动线程 | 创建/setAutoCommit(false)/TypeRegistry 与 DefaultValueConverter 装载(只读查询) | 无——reader 尚未创建 |
| 快照(恒 skipped)`SkippedSnapshotSource.execute` | coordinator 线程 | `initialContext`(读 xlog 位点,`txid_current()` 会分配 XID)+ **随即 commit 收敛** | 无——快照阶段先于 streaming execute |
| streaming 装配 `PostgresStreamStreamingChangeEventSource.execute`/`init` | coordinator 线程 | `initialOffsetWithCommit`(同上,读后 commit) | 无——reader 线程在最后一次 init 查询之后才 start |
| 'R' enrich | **reader 线程独占** | `RelationTableFactory(RelationMetadataSource.jdbc(mainConnection, ...))`——DDL 稀疏,罕见查询 | 装配后 main 连接仅此一线程使用 |
| 停机 `doStop` | Connect 停机线程 | close | reader 已由 `stopStreaming` 的 session.close → join 收敛在前 |

要点与注记:

- **无 xmin 拉取**:vanilla 的周期 xmin 刷新(读 slot xmin)不复刻,xmin 恒缺省——不存在
  该查询与 'R' enrich 的并发面(设计 §5.6 已记)。
- **心跳 action query 不占 main 连接**:dispatcher 装配时 `HeartbeatFactory` 拿到的是连接
  **工厂**(每次 action 新建 `PostgresConnection`),且 `heartbeat.action.query` 缺省空
  (no-op)——与 reader 的 'R' enrich 无连接争用。
- **initialContext 读后 commit(Task 8 新增)**:`txid_current()` 会在 autoCommit=false 的
  main 连接上强制分配 XID,不提交则该事务悬置到停机——复制会话在**另一条连接**上执行的
  `pg_create_logical_replication_slot` 为等解码一致点会等它,连接器自死锁(IT 首跑实测修复,
  `SkippedSnapshotSource`/`initialOffsetWithCommit` 两处,详见 task-8-report)。
- **MS5 预警**:真快照接入后,快照的 schema 读取与 reader 的 'R' enrich 将并发共享 main
  连接——届时必须串行化(连接级互斥或快照专用连接),本审计的"时序独占"论证以快照恒
  skipped 为前提。
- bean registry 专属连接(Task 8 补齐的 vanilla 命名豆)是**独立新连接**(`connectionFactory.
  newConnection()`),不复用 main——不引入新并发面。

## 附:D7 停机语义(IT 钉位)

- `stopStreaming` 次序:session.close(reader ≤100ms 退出,stopping 置位使断连不算失败)→
  reader.join(5s)→ `assembler.shutdownFast()`(毒丸+interrupt,**不排干**)——已提交未输出
  事务由复制槽重发(at-least-once)。
- IT 侧可观测钉位:`EndToEndStreamedTxIT.restartResumesAndDeliversAllCommittedRowsAtLeastOnce`
  (重启后已提交事务全量到达,重复允许)、`FrontierCapIT`(未输出事务钉住 confirmed_flush)。
- 测试确定性断言走 `close()` 排干的口径在引擎模块既有测试(`ReaderUnblockedTest` 等)保持;
  连接器侧 D7 的"不排干"以 shutdownFast 实现、以重启 IT 钉住行为面。

## 附:审计外发现(已随 Task 8 修复)

1. 任务装配缺 BeanRegistry 命名豆(vanilla :151-159)——`SnapshotterServiceProvider` 经
   `lookupByName("ConnectorConfig")` 取配置,缺失即 NPE;已补齐七项命名豆 + bean registry
   专属连接的创建/停机收敛。
2. 事务 id 前缀(`xid-`)与元数据提供者不同源——每事务多一对空 BEGIN/END;已改纯数字
   形态(vanilla 同款)。
